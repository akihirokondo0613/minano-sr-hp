# 局所UIの変更

文言、写真、配色、レイアウト、挙動のうち、対象ページの対象箇所だけで完結する修正に使う。共通CSS・JS、記事テンプレート、生成器、監査、CI、公開構造へ波及する場合は局所修正ではない。[共通資産の変更](change-common-assets.md)へ切り替える。

## 変更範囲を固定する

着手前に次を一文ずつ決める。

- 対象ページと要素
- 対象画面と、影響を受けるブレークポイント
- 維持する文言、画像、配色、リンク、別画面の見え方
- 完了を判定できる表示・操作条件
- 変更予定ファイルと直接の同期先

途中で別の問題を見つけても、今回の完了に不可欠でなければ混ぜない。共通資産へ広がる証拠が出るまでは全ページ監査へ拡大しない。

## 現状を再現する

1. `rg`で対象HTML、適用元CSS、後勝ちの上書きCSS、関連JSだけを特定する。
2. 対象幅で画面と計算済みスタイルを確認する。
3. 不具合なら、変更前のスクリーンショット、要素矩形、console／page error、操作手順を残す。
4. モバイルとPCの一方だけが対象でも、もう一方を維持条件として把握する。

CSSの競合は同じプロパティだけでなく、`border-bottom`と`text-decoration`のように別の描画手段が重なっていないかも確認する。旧実装がJS注入CSSや別系統のCSSに残る場合は、除外フラグを増やすのではなく適用元を一本化する。ナビ下線の過去事例は[二重下線の事故](incidents/nav-double-underline.md)を参照する。

## 最小差分で直す

- 対象箇所だけを編集し、周辺のコピー、ブランドトークン、余白、別ページを整え直さない。
- 既存コンポーネント、既存クラス、既存トークンで解けるなら新しい表現を増やさない。
- ホバーやトランジションは`padding`、`width`、`margin`など再レイアウトを起こすプロパティを動かさず、`transform`と`opacity`を使う。
- ページ固有CSSで済む変更を安易に共通CSSへ入れない。共通側を変える必要がある場合は作業分類を変更する。
- トップのファーストビューを変える場合、`index.html`の生成済みCritical CSSを手作業で直さない。[共通資産の変更](change-common-assets.md)の同期手順を使う。
- 日本語の改行、nowrap、`<wbr>`を触る場合は[日本語組版とレスポンシブ](typography-responsive.md)に従う。

## 現行デザインで維持するもの

次は過去に比較・巻き戻しまで行って確定した構造である。変更依頼に含まれない限り、整理や統一を理由に作り替えない。具体的な寸法・色・ブレークポイントは、文書の固定値ではなく現在のHTMLとCSSを正本とする。

- トップは短い入口で、サービス、料金、支援の進め方、事務所案内の詳細ページへ分けている。外部ブックマーク互換のためトップに残した既存アンカーを削除・改名しない。
- トップの 06 TOPICS は、自動では動かさない横送りのカード列。スワイプと見出し行の前後ボタンで送る。2026-08-23に自動スクロール（無限マーキー）を試して不採用と判断済みなので、動かす案へ戻さない。送りはCSSのスクロールスナップが担い、ボタンは `scrollBy()` を呼ぶだけ。JSが無くても素の横スクロール列として使える。カードは小さく、狭い画面でも2枚ぶん見える幅を保つ。3件の縦リストへも戻さない。カードと公開本数は `scripts/sync-home-topics.mjs` の生成物で、手書きしない。サムネイルは `blog.html` の一覧が持つ記事ごとのSVGの写しで、図の正本は一覧側に置く。
- ヒーローの `.hero-spot` は直近のスポット業務の受付カード。期間限定なので、見直し時期を `index.html` のコメントに書き、時期が過ぎたら中身を差し替えるかブロックごと消す。制度の数値は確定前なら「見込み」を落とさない。
- 05 よくある質問の左カラムは追従（`position: sticky`）させない。2026-08-23に見え方が悪く不採用と判断済み。
- ナビは8項目（サービス／助成金／料金／支援の進め方／事務所案内／ブログ／社労士とは／公式情報）。区切り線と中間幅の間引きは `nth-child` 依存なので、増減するときは `skin-v2.css` のナビ規則とタブレット幅の2列グリッドを同時に直す。
- トップの全長は390px幅で9500pxが上限（`scripts/verify-ui.cjs`）。要素を足すときは削る場所も一緒に決める。
- トップのサービス一覧は、写真カードではなく番号付きの横長行リスト。サービス、成長段階、記事一覧、事務所紹介等のイラストは、人物や小物を切らない `contain` と既存の縦横比を維持する。
- 助成金の工程表示は事前計画の必要性と受給保証ではない注記を残す。削除済みのCASE段階ハイライトとCTAの光沢演出を復活させない。
- トップのヒーロー画像、白いベール、説明文、二つのCTA、trustチップは、個別の変更依頼がない限り一組として維持する。スマホだけの修正でPCや写真の濃さを変えない。
- 大画面向けのトップ調整は `index.html` の既存大画面ブロック、下層ページは `wave-skin.css` の既存共通層で行う。ブログ本文幅を下層ページの拡大へ巻き込まない。
- `portal.html` は公的機関への外部リンク集。配布ファイル、検索、フィルターへ戻さず、リンクを変えるときは説明と表示ドメインも同期する。
- 線画アイコンと緑のチェックは現行デザイン。行政機関の漢字チップだけが承認済みの例外であり、全アイコンのモノグラム化を再実施しない。
- ホバー下線はルート系と `uploads/` 系でそれぞれ一系統にする。JavaScript注入CSSで同じ装飾を重ねない。
- 採用ページの公開条件、料金・勤務地等は表示中のコードと所有者確認を優先する。過去文書の確定表現だけで変更しない。
- 問い合わせフォームの送信方式と送信先は、現行コードと実際の受信試験を確認してから変える。圧迫感のある入力案内を追加しない。
- 共通フッターの所在地、電話、営業時間、メールの改行構造をページごとに独自化しない。表示、テンプレート、構造化データを同時に確認する。

大規模な見た目変更の採否と巻き戻し経緯は[デザイン変更の履歴](incidents/design-history.md)を参照する。

## 対象回帰を測る

変更前と同じ条件に加え、対象ブレークポイントの直前・境界・直後を測る。スマホ変更の基準候補は`320px`、`390px`、`430px`だが、実装のブレークポイントと実機幅を優先する。

- 依頼箇所のスクリーンショットを比較する。
- `getBoundingClientRect()`で要素の左右端を測り、`documentElement.scrollWidth`だけで合否を決めない。
- 横はみ出し、重なり、文節途中の改行、泣き別れ、クリック領域を確認する。
- リンクとボタンはキーボード操作、フォーカス表示、原則`24px × 24px`以上の操作領域を維持する。
- console errorとpage errorを確認する。
- モバイル修正なら維持対象のPC幅、PC修正なら維持対象のモバイル幅も代表一条件で確認する。

局所修正は対象テストと`node scripts/preflight.mjs`を通せばよい。共通CSS・JS、共通テンプレート、生成器、サイト構造を変えた場合だけ`node scripts/run-layout-checks.cjs --full`などの全体回帰へ広げる。最終差分が変わっていなければ合格済みの重い検証を繰り返さない。

公開を伴う場合は[GitHub経由の編集・本番公開](release.md)へ進む。
